## 一、現況實測結果

檢測對象：`成品/2026-08/0818-大盤小報-今天行情非常挑股票，-直式.mp4`
（與 `out/output-dapan.mp4` 同一組設定，其他 composition 走的也是同一套 `remotion render --crf 23 --audio-bitrate 128k`，所以結論可以類推）

**12 項規格 → 符合 5 項、不符合 5 項、待確認 2 項。**

| # | 規格要求 | 實測值 | 判定 |
|---|---|---|---|
| 1 | MP4 容器 | `mov,mp4` | ✅ |
| 2 | faststart（moov 置前） | moov @40，mdat @78843 | ✅ |
| 3 | H.264 High profile | High | ✅ |
| 4 | 1080×1920 直式、不加黑邊 | 1080×1920 | ✅ |
| 5 | 30 fps 固定 CFR | 30/1，每格 0.03333 秒一致 | ✅ |
| 6 | 2 個連續 B-frame | has_b_frames = 2 | ✅ |
| 7 | AAC-LC / 128 kbps / 48 kHz / 立體聲 | LC、125 kbps、48 kHz、2ch | ✅ |
| 8 | **響度 −14 LUFS、峰值 −1 dBTP** | **−12.0 LUFS，True Peak +0.2 dBTP** | ❌ |
| 9 | **色彩明確標記 bt709**（primaries/transfer/matrix 皆填） | primaries=unknown、transfer=unknown、matrix=**bt470bg** | ❌ |
| 10 | **yuv420p、8-bit** | **yuvj420p**（full range） | ❌ |
| 11 | **closed GOP，長度 15** | **GOP = 250**（x264 預設，等於沒設） | ❌ |
| 12 | **Level 4.1** | Level 4.0 | ❌ |
| — | 位元率 目標 5 Mbps／上限 6 Mbps | 3.19 Mbps | ⚠️ 待確認 |
| — | 容器 brand `mp42` | `isom`（compatible: isom/iso2/avc1/mp41） | ⚠️ 待確認 |

### 其中兩項不只是「紙上不合規」，是真的影響成品

- **True Peak +0.2 dBTP** —— 已經超過 0，代表音訊實際上在削波。這是現在就該修的問題，跟規格無關。
- **色彩標成 bt470bg + full range** —— bt470bg 是 PAL 的色彩矩陣，跟內容完全不符。加上被標成 full range（yuvj），在部分播放器與平台轉碼後顏色會偏。

### 成因

不合規的項目全部來自同一個原因：**目前只用 `remotion render --crf 23` 出片，沒有任何編碼參數控制。**
GOP 250 是 x264 的預設值、Level 4.0 是編碼器自動推算、yuvj420p 是 Remotion 用 JPEG 當中間影格格式的副作用（`remotion.config.ts` 裡的 `Config.setVideoImageFormat('jpeg')`）、色彩標籤則是根本沒人填。

## 三、提案做法

### 插入點

`server/index.js` 約 980–1010 行的「收成品」段落。目前是：

```
out/output-*.mp4  ──copyFileSync──▶  成品/2026-08/0818-大盤小報-…-直式.mp4
```

改成：

```
out/output-*.mp4  ──ffmpeg 交付轉檔──▶  成品/2026-08/0818-大盤小報-…-直式.mp4
                   （橫式／投廣版仍走原本的 copyFileSync）
```

**渲染流程完全不動**，Remotion、run.js、所有 `npm run render:*` 都維持原樣。只有「複製到成品庫」這一個動作被換掉。失敗時要能退回 copyFileSync，不能因為轉檔掛掉就沒有成品。

### 轉檔指令（已在本機實測驗證通過）

**Pass 1 —— 量測響度**

```bash
ffmpeg -hide_banner -i IN.mp4 \
  -af loudnorm=I=-14:TP=-1:LRA=11:print_format=json -f null - 2>&1 | tail -20
```

取出 `input_i` / `input_tp` / `input_lra` / `input_thresh` / `target_offset` 五個值。

**Pass 2 —— 交付轉檔**

```bash
ffmpeg -y -i IN.mp4 \
  -c:v libx264 -profile:v high -level:v 4.1 -preset slow \
  -crf 21 -maxrate 5M -bufsize 10M \
  -x264-params "keyint=15:min-keyint=15:scenecut=0:open-gop=0:bframes=2" \
  -vf "scale=in_range=pc:out_range=tv,format=yuv420p" \
  -colorspace bt709 -color_primaries bt709 -color_trc bt709 \
  -r 30 -fps_mode cfr \
  -af "loudnorm=I=-14:TP=-1:LRA=11:measured_I=<input_i>:measured_TP=<input_tp>:measured_LRA=<input_lra>:measured_thresh=<input_thresh>:offset=<target_offset>:linear=true,aresample=48000" \
  -c:a aac -profile:a aac_low -b:a 128k -ar 48000 -ac 2 \
  -movflags +faststart -brand mp42 \
  OUT.mp4
```

### 幾個參數為什麼這樣寫

| 參數 | 理由 |
|---|---|
| `scale=in_range=pc:out_range=tv,format=yuv420p` | **不能只改標籤。** 源被標成 yuvj（full range）+ bt470bg，但實際內容是 bt709 的網頁畫面、標籤本身就是錯的。若讓 ffmpeg「相信」錯標籤去做 matrix 轉換，顏色會被改壞。這裡只做 range 壓縮（pc→tv），不碰 matrix，再由輸出端重新打上正確的 bt709 標籤。 |
| `-colorspace / -color_primaries / -color_trc` 三個都給 | 規格第 9 項要求 primaries / transfer / matrix **皆填**，缺一項就不算標明確。 |
| `scenecut=0` + `open-gop=0` | 沒關掉場景偵測的話 x264 會臨時插 I-frame，GOP 長度就不會是固定 15。`open-gop=0` 才是 closed GOP。 |
| `aresample=48000` | **容易漏。** ffmpeg 的 loudnorm 內部會把音訊升到 192 kHz，不接 aresample 就不是 48 kHz 了，規格第 7 項會掛。 |
| `linear=true` + two-pass | 單趟 loudnorm 是 dynamic 模式、會做動態壓縮，語音聽起來會怪。two-pass 只多花兩三秒，用線性增益，聽感不變。 |
| `-brand mp42` | 把 major_brand 從 isom 改成 mp42。 |

### 實測驗證

上面這串指令我已經跑過完整驗證（用同樣是 yuvj420p 的 1080×1920 測試素材），逐項確認：

```

color_space=bt709   color_transfer=bt709   color_primaries=bt709

GOP 長度分布：{15: 全部}   moov @40 早於 mdat @4536

```

**12 項全數通過。** 指令本身沒有問題，剩下的風險都在「套到你的真實素材上會怎樣」。

## 四、三個要注意的風險

### 1. GOP 15 是這裡面最貴的一項 ⚠️ 最需要實測

0.5 秒一個 I-frame，關鍵影格密度變成現在的 **16 倍**。同樣品質下位元率會明顯往上跑。

現在是 3.19 Mbps，改完很可能逼近甚至撞到 `maxrate 5M`。撞到頂就會開始削畫質，而**你的內容剛好是最怕這個的類型**：K 線的細線條、字幕邊緣、APP 截圖的小字，都是高頻細節，被壓縮器犧牲時最明顯。

規格自己寫「建議用 CRF 21 + maxrate 5M 品質導向」，代表它不是強制 CBR，所以位元率落在 3～5 之間應該都可接受。但**這一項沒辦法用推的，要實壓一支看數字**。

### 2. 這是二次壓縮

Remotion 已經用 CRF 23 壓過一次，這裡再壓一次。CRF 21 比 23 嚴格，encoder 會盡量保留，實務上多半看不出來 —— 但疊上 GOP 15 之後就不一定了。

如果實測發現字幕糊掉，替代方案是改走「中間檔」流程：讓 Remotion 輸出接近無損的中間檔（`--crf 1` 或 ProRes），再由 ffmpeg 一次壓成交付檔，全程只壓一次。代價是中間檔很大、渲染變慢。**先照現在的簡單路線做，不滿意再升級。**

### 3. 色彩轉換要肉眼比對

第 9、10 項的修正會實際改動畫面亮度（full range → limited range）。理論上做法是對的，但**上線前一定要把轉檔前後兩支並排看一次**，特別注意深色背景和品牌色有沒有跑掉。

## 五、驗收指令

轉檔後拿這串逐項對規格：

```bash
F=成品/2026-08/你的檔案.mp4

# 影像 / 音訊 / 容器
ffprobe -v error \
  -show_entries stream=codec_name,profile,level,width,height,pix_fmt,color_range,color_primaries,color_transfer,color_space,has_b_frames,r_frame_rate,sample_rate,channels \
  -show_entries format=bit_rate -show_entries format_tags=major_brand -of default "$F"

# GOP 長度（應該全部是 15）
ffprobe -v error -select_streams v:0 -show_frames -of json "$F" | python3 -c "
import sys,json,collections
f=json.load(sys.stdin)['frames']
ks=[i for i,x in enumerate(f) if x.get('key_frame')==1]
print(collections.Counter([b-a for a,b in zip(ks,ks[1:])]).most_common())"

# faststart（moov 要在 mdat 前面）
ffprobe -v trace -i "$F" 2>&1 | grep -m3 -E "type:'(moov|mdat|ftyp)'"

# 響度（Integrated 要 ≈ -14，True Peak 要 ≤ -1）
ffmpeg -hide_banner -nostats -i "$F" -af loudnorm=I=-14:TP=-1:print_format=summary -f null - 2>&1 | tail -12
```

期望值：

```
profile=High  level=41  pix_fmt=yuv420p  color_range=tv
color_primaries=bt709  color_transfer=bt709  color_space=bt709
has_b_frames=2  r_frame_rate=30/1  sample_rate=48000  channels=2
major_brand=mp42   GOP 分布 = [(15, N)]   moov 早於 mdat
Input Integrated ≈ -14.0 LUFS   Input True Peak ≤ -1.0 dBTP
```

## 六、待跟客戶／平台確認的兩件事

1. **位元率的判定方式。** 規格寫「目標 5 Mbps、上限 6 Mbps」，但同一欄又寫「建議用 CRF 21 + maxrate 5M 品質導向」—— 這兩句是矛盾的。想確認：檢核是只看「不超過 6 Mbps」，還是會要求「必須接近 5 Mbps」？如果是後者，得改用 two-pass ABR 而不是 CRF。

2. **`mp42` brand 是否真的在檢核項目裡。** 現在輸出是 `isom`（compatible brands 已含 `mp41`、`avc1`），絕大多數平台都吃。若對方只是照抄範本、實際不驗，這項可以不做。
